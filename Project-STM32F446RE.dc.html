01

Why this project

Generated code hid the part I wanted to learn.

Coursework and tutorials both start you in a configurator: click a pin, get a driver, blink an LED. It works, and it teaches you almost nothing about the peripheral. When something misbehaves — a clock tree left at default, a timer prescaler off by one — you have no mental model to debug with.

So I started this repo with one rule: every peripheral gets written from the reference manual first. Read the register map, write the minimal driver, prove it on the board with a scope or logic analyzer, then compare against what the HAL would have generated and note where mine is worse.

The goal isn't to avoid the HAL forever. It's to be the person on the team who can explain what it's doing.

Rule. Reference manual before any library.
Rule. Every driver proven on hardware, not in a debugger only.
Rule. Commit the notes, not just the code.

03

Process

Each module follows the same loop: read the register map, write the smallest driver that can be wrong in an obvious way, verify it on the board, then write down what surprised me. The order below is deliberate — nothing depends on a peripheral I haven't understood yet.

01 — Startup & linker script. Vector table, reset handler, .data/.bss init, stack placement — the parts every project inherits and nobody reads. First time I saw exactly where main comes from.
02 — RCC & GPIO. Clock enable per bus, mode/pull/speed registers, then a blink I can explain register by register. Verified pin timing on the logic analyzer rather than trusting the delay loop.
03 — Clock tree to 180 MHz. PLL configuration, flash latency, bus prescalers — and confirming the result on MCO with a scope instead of assuming the math was right.
04 — Timers & UART. A real microsecond delay from a general-purpose timer, then printf-over-UART so the board can talk back. Baud divisor derived from the clock config, not copied from a tutorial.
05 — Interrupts, then DMA. NVIC priorities, EXTI on a debounced button, and moving UART traffic off the CPU with DMA — measured with a GPIO toggle around the ISR.
04

Decisions & tradeoffs

Registers by hand instead of STM32CubeMX

Drivers are written against the reference manual with CMSIS headers for the register definitions only.

Cost: much slower, and my drivers are less portable than the HAL's. Why anyway: I can now read a HAL function and tell what it configures — which is the point.

Makefile + GCC instead of an IDE project

Plain Make, explicit compiler and linker flags, OpenOCD for flashing — so the build is inspectable and works the same on any machine.

Cost: no one-click debug UI; I set up GDB myself. Why anyway: nothing about the build is a mystery, and it maps directly to CI later.

Verify on hardware, not in the debugger

Every module ships with a measurement: a logic-analyzer capture, a scope shot on MCO, or a GPIO toggle around the critical section.

Cost: slower per commit; needs the bench. Why anyway: it caught a wrong flash latency that ran "fine" in the debugger.

What I'd do differently

1. Write the README as I go. The code landed before the notes. Documenting each peripheral while it's fresh — register quirks included — would make the repo far more useful to anyone reading it, including future me.

2. Set up a test target earlier. A host-side build with the register block mocked would let me unit-test driver logic without the board, and would have caught two off-by-one prescaler bugs before flashing.

3. Pick one end goal for the drivers. Learning peripheral-by-peripheral is fine, but a target application — a small data logger, say — would force the modules to work together and surface the integration problems that matter in real firmware.
